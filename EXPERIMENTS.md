## 2026-11-07 · Фаза 0. Підготовка

**Питання дня.** Чи можна розробляти агента на 27B без локальної GPU і майже
без витрат, і що в плані треба змінити, перш ніж писати перший рядок клієнта?

**Розглянуті варіанти.**
- Розробка: 27B через hosted API з першого дня · мала модель локально в Ollama.
- Генерація траєкторій (фаза 9): API · орендована GPU з vLLM.
- Перевірка типів: pyright (як у плані) · mypy --strict (уже знайомий).
- Ліцензія: MIT · Apache-2.0.
- ADR: без них, усе в журналі · ADR на кожне рішення · 3–4 ADR на весь проєкт.
- Хто пише код: все пише автор · все пише Claude · розподіл за темою.

**Що зроблено.**
- Перевірено модель за сторонніми джерелами (HF був недоступний): Apache 2.0,
  262K контексту нативно, thinking увімкнений за замовчуванням.
- Перевірено tool calling на `qwen2.5:3b-instruct-q4_K_M` через Ollama.
- Скелет репо: uv, ruff, mypy --strict, pytest, Makefile, smoke-тест,
  CI на GitHub Actions, design doc, ADR 0001.

**Числа.**
- Tool calling на 3B локально: працює, `finish_reason: "tool_calls"`,
  правильний інструмент і аргументи (один ручний запит, не eval).
- `make check`: 10 тестів, усі зелені.
- Оцінка вартості фази 9 (розрахунок, не вимір): API ≈ $103 за 30M вихідних
  токенів проти ≈ $5–10 на орендованій GPU; вимкнення thinking зменшує
  API-оцінку з ≈ $130 до ≈ $50 на тисячу траєкторій.

**Висновок.**
- Фази 0–8 — на малій локальній моделі за $0; 27B тільки у фазах 3, 9, 10.
- Фаза 9 — на орендованій GPU, не в API.
- mypy --strict, Apache-2.0, 3–4 ADR на проєкт.
- Обв'язку пише Claude; цикл агента, інструменти, sandbox, permissions,
  метрики evals і оракули пише автор.

**Що досі незрозуміло.**
- Офіційні факти про модель: commit-ревізія на HF, чи є окремий
  Instruct-варіант, формат tool calls у chat template.
- Чи допомагає thinking coding-агенту настільки, щоб виправдати вартість —
  вимірюється у фазі 3.
- `usage` в Ollama не має лічильника reasoning-токенів; як його повертає
  провайдер 27B — перевірити у фазі 1.

## 2026-11-07 · Фаза 1. Шар доступу до моделі

**Питання дня.** Як зробити один клієнт, що однаково працює з Ollama і з
hosted 27B, ретраїть тільки те, що можна, і рахує токени, гроші, latency і
TTFT на кожен виклик?

**Розглянуті варіанти** (записано до реалізації).
- Sync чи async клієнт: sync простіший · async дає паралельний eval runner у
  фазі 3 без потоків. → async.
- Retry: `tenacity` (уже в залежностях) · вбудовані retry `openai` SDK ·
  власний цикл. Вбудовані не відрізняють retry до першого токена і посеред
  стріму, `tenacity` ховає логіку за декораторами. → власний цикл з
  ін'єкцією `sleep` і `rng` для тестів, SDK retry вимкнені (`max_retries=0`),
  `tenacity` прибрати.
- Retry посеред стріму: ретраїти завжди · тільки до першого токена. Після
  першого токена користувач уже бачив частину відповіді. → тільки до першого
  токена.
- Backoff: експоненційний без jitter · equal jitter · full jitter. → full
  jitter, `Retry-After` має пріоритет, якщо сервер його дав.
- Мокання HTTP у тестах: `pytest-httpserver` (справжній сервер) · `respx`
  (мок транспорту httpx, на якому стоїть `openai`). → `respx`, швидше й
  детерміновано.
- Ревізія локальної моделі: тег Ollama · digest. Тег рухомий. → digest у
  конфізі.
- Під час реалізації: `openai` SDK 3.x працює на `httpx2`, а `respx` патчить
  тільки `httpx`. → замість `respx` тести підставляють
  `httpx2.MockTransport` через `http_client`. Ще один фейковий сервер не
  потрібен.

**Що зроблено.**
- `configs/models.yaml`: `local-small` (qwen2.5 3B), `local-tiny` (0.5B),
  `qwen27b-hosted` (OpenRouter). Локальні моделі запінені на digest, hosted —
  на датований знімок.
- `llm/`: стрімінговий async-клієнт, класифікація помилок, full-jitter
  backoff з пріоритетом `Retry-After`, загальний дедлайн, облік токенів
  (включно з cached і reasoning), вартості, latency, TTFT і швидкості
  декодування. `reasoning_content` / `reasoning` іде окремо від `content`.
- CLI: `agent chat` (one-shot і REPL), `agent models`.
- Тести: 64 юніт-тести без мережі; 2 живі (`make test-live`) на Ollama.

**Числа** (ноутбук, CPU, Ollama 0.34.2, 5 викликів, промпт 40 токенів,
`max_tokens=80`, після прогріву).

| модель | TTFT, медіана | latency, медіана | декодування, медіана |
|---|---|---|---|
| `local-tiny` (0.5B Q8) | 0.03 с | 1.82 с | 44.6 tok/s |
| `local-small` (3B Q4_K_M) | 0.10 с | 6.60 с | 11.9 tok/s |

- TTFT такий малий, бо Ollama кешує префікс: 39 із 40 вхідних токенів
  прийшли як `cached_tokens`. Холодний перший виклик 3B — 0.48 с.
- Живий tool call на 3B: правильний інструмент і аргументи (2/2 живих
  тести).

**Висновок.**
- Клієнт однаковий для будь-якого OpenAI-сумісного endpoint; модель
  перемикається аліасом.
- 12 tok/s на 3B означає, що агентна задача на 2–3 тисячі вихідних токенів
  займе кілька хвилин. Для розробки циклу прийнятно, для evals на ноутбуці —
  ні: eval-прогони фази 3 мусять іти на 27B через API.
- **Контекст Ollama — 4096 токенів**, хоча модель підтримує 32K, і через
  OpenAI-сумісний endpoint це не змінити. Схеми інструментів плюс історія
  швидко це переповнять, а Ollama обріже промпт мовчки. Перед фазою 2
  треба або запустити Ollama з `OLLAMA_CONTEXT_LENGTH=16384` (KV cache 3B ≈
  36 КБ/токен → ≈ 0.6 ГБ на 16K), або рахувати бюджет під 4K.

**Що досі незрозуміло.**
- Критерій «`--model qwen27b-hosted` поводиться так само» **не перевірений**:
  потрібен ключ OpenRouter, тобто гроші автора. Код шляху той самий, тест
  на відсутній ключ є.
- Як OpenRouter стрімить `reasoning` для Qwen3.8 і чи віддає
  `reasoning_tokens` у `usage` — перевірити з першим ключем.
- `Retry-After` у форматі HTTP-дати ігнорується (падаємо на backoff) —
  свідомо, поки не зустрінеться провайдер, який так робить.

## 2026-11-07 · Фаза 2. Ядро агента, MVP

**Питання дня.** Який мінімальний цикл з інструментами, sandbox і
permissions дає агентові самому виправити падаючий тест — і як тестувати
його детерміновано, без моделі?

**Розглянуті варіанти** (записано до реалізації).
- Де виконуються файлові інструменти: усе через `docker exec` · read/edit
  на хості з path guard, у контейнері тільки `bash`. Файлова операція — не
  виконання виводу моделі, а `docker exec` на кожне читання — сотні мс. →
  файлові інструменти на хості, `realpath` має лишатися всередині workspace
  (ловить і `../`, і симлінк, створений моделлю через `bash`).
- Workspace: git worktree · локальний clone · каталог як є. У worktree
  `.git` — це файл зі шляхом хоста, тож git у контейнері не працює; clone
  втрачає незакомічені зміни. → для MVP каталог як є (in-place, як Aider і
  Claude Code); evals у фазі 3 самі робитимуть свіжу копію на задачу.
- `grep`: ripgrep (на хості не встановлений) · `grep -rn` у контейнері ·
  Python `re` на хості. → Python: без залежності, тестується без Docker.
- Bash-правила: fnmatch по всьому рядку · розбір shell. Розбір shell
  обходиться (`ls; rm -rf`). → deny — підрядки/regex будь-де (best effort),
  auto-allow тільки для команд без метасимволів `; & | \` $( > <`. Справжня
  межа — sandbox, не правила.
- Зациклення: зупинка · попередження моделі. → зупинка, як у плані; варіант
  з попередженням — кандидат на абляцію у фазі 3.
- Контекст 3B в Ollama (4096): системний сервіс без sudo не змінити ·
  `ollama create` з `PARAMETER num_ctx` поверх тих самих ваг. → друге, нова
  модель без перезавантаження ваг.


**Що зроблено.**
- Інструменти `read_file`, `list_dir`, `glob`, `grep`, `edit_file`,
  `write_file`, `bash`; схеми з pydantic; помилки → observation.
- Path guard з розв'язанням симлінків; секретні файли (`.env`, ключі) не
  читаються і не потрапляють у `grep`.
- Docker sandbox: `--network none`, `--cap-drop ALL`, read-only root,
  uid користувача, ліміти пам'яті/CPU/процесів, єдиний mount — workspace.
- Permissions: `read-only` / `ask` / `auto`, deny-правила, allow-list, який
  ламається метасимволами shell, захищені шляхи, підтвердження з diff.
- Цикл з бюджетами (ходи, токени, гроші, час, заповнення контексту),
  детектором зациклення і підштовхуванням після порожньої відповіді.
- CLI: headless `agent -p ... --output json` і REPL.

**Числа.**
- Тести: 183 юніт (FakeLLM, FakeSandbox) + 7 проти справжніх контейнерів
  (немає мережі, не root, не пише поза workspace, таймаут), обидва набори
  в CI.
- Демо-задача (off-by-one) на `local-small`, ручні прогони, не eval:

| серія | що змінено перед нею | виправлено | як закінчились |
|---|---|---|---|
| перший прогін | — | 0/1 | модель перестала викликати інструменти на 3-му ході |
| 3 прогони | шаблон Ollama v1 | 0/3 | tool calls приходили текстом |
| 3 прогони | шаблон Ollama v2 | 0/3 | 2× зациклення на `list_dir("")`, 1× зламані відступи |
| 5 прогонів | `""` = корінь, промпт | 0/5 | 3× порожня відповідь як «готово», 2× діагноз без правки |
| 3 прогони | підштовхування після порожньої | 0/3 | повтор невдалого `edit_file`; порожніх відповідей 0 |

  Друга серія з 5 обірвалась на 3-му прогоні: я видалив каталог демо-задачі,
  поки серія з нього копіювала (вона переїхала в golden set). Прогони 4–5
  відкинуті, позначка «тести змінено» в прогоні 3 недостовірна.

**Висновок.**
- Обв'язка працює від кінця до кінця: агент читає, шукає, редагує і
  запускає тести в sandbox. Межа — 3B-модель, а не цикл.
- Найдорожча знахідка — не в моєму коді: шаблон Ollama губив tool calls з
  історії. Без читання сирих траєкторій це виглядало б як «модель погана».
  Звідси правило: кожен збій спершу перевіряти на рівні серверу й шаблону.
- Кожен клас збою записаний у `docs/failure_taxonomy.md`.

**Що досі незрозуміло.**
- Критерій «готово» фази 2 («27B сам виправляє баг») не перевірений: немає
  ключа. На 3B — 0 із 15 ручних прогонів.
- Чи варто показувати моделі найближчі рядки, коли `old_string` не
  знайдено (клас 8), — кандидат на абляцію у фазі 3.

## 2026-11-07 · Фаза 3. Evals

**Питання дня.** Як отримати число «агент працює на N% задач» з довірчим
інтервалом, і як CI зловить регресію, не палячи гроші на кожен коміт?

**Розглянуті варіанти** (записано до реалізації).
- Де код runner-а: `evals/runner.py` скриптом (як у плані) · пакет
  `agent.evals` під mypy і тестами. → пакет; дані задач лишаються в `evals/`.
- Запуск агента в runner-і: subprocess `agent -p ... --output json` · той
  самий `Agent` in-process. Subprocess чесніший (той самий шлях, що в
  користувача), in-process дає FakeLLM-тести runner-а. → in-process, але з
  тими самими компонентами, що й CLI.
- Захист від «виправив тести замість коду»: довіряти · перед оцінкою
  повертати оригінальні тестові файли й докладати приховані тести. → друге.
- pass@k: наївна частка · незміщена оцінка Chen et al. (2021). pass^k: як у
  τ-bench, C(c,k)/C(n,k). → обидві незміщені.
- CI на pass rate: bootstrap по задачах · біноміальний інтервал. Задачі
  різні за складністю, тож одиниця незалежності — задача. → percentile
  bootstrap по задачах, парний bootstrap для порівняння двох прогонів.
- Gate у CI: на кожен PR · за лейблом `eval`. → за лейблом, і тільки якщо є
  секрет з ключем.
- LLM-as-judge і SWE-bench Verified: зараз · пізніше. Суддю треба валідувати
  на розмітці автора, SWE-bench потребує хмарної машини. → пізніше, у
  статусі.


**Що зроблено.**
- Пакет `agent.evals`: runner (свіжа копія на прогін, k прогонів, оцінка в
  новому sandbox з відновленими тестами і прихованими тестами), незміщені
  pass@k і pass^k, bootstrap по задачах, парний bootstrap, markdown-звіти,
  `agent eval tasks | toolcalls | report | compare`.
- Golden set v0: 12 задач (11 bugfix, 1 feature), у 6 є приховані тести, у
  кожної — еталонне рішення. Docker-тест перевіряє оракул: без фіксу
  падає, з фіксом проходить — 12/12.
- 30 одно-крокових tool-call кейсів.
- `.github/workflows/eval-gate.yml` за лейблом `eval`; без секрету і
  baseline чесно пропускається з notice.

**Числа.**
- Tool-call eval, `local-small`, k=1, 30 кейсів
  (`evals/results/2026-11-07T1913_toolcalls_local-small_system.v1.md`):
  точність **66.7% [50.0%, 83.3%]**, невалідний JSON 0%, без виклику 6.7%;
  correct 20, wrong_args 5, wrong_tool 3, no_call 2.
- Baseline golden set на `local-small` **не завершений**: зупинений на 5-му
  з 36 прогонів (сесію закрито). На той момент 0/5, усі `completed`.

**Висновок.**
- Інструмент вимірювання готовий і сам протестований (258 тестів), але
  першого числа pass@1 ще немає.
- Інтервал на 30 кейсах — ±17 п.п. Щоб розрізняти зміни в 5 п.п., треба на
  порядок більше кейсів або повторів.

**Що досі незрозуміло / відомі вади.**
- **Баг грейдера tool-call eval:** аргумент, якого модель не передала,
  перевіряється як `None`, а не як значення за замовчуванням зі схеми.
  `list-root` з `list_dir({})` зарахований як провал, хоча це `path="."`.
  Baseline 66.7% занижений щонайменше на один кейс. Виправити: валідувати
  аргументи через `tool.Args` перед матчингом, перезапустити baseline.
- Baseline запущено на незакоміченому коді (`git d6669df-dirty`) — після
  виправлення грейдера перезапустити на чистому коміті.
- Ollama один раз не надіслав `usage` у стрімі → вартість прогону
  «невідома». Для локальної моделі це $0, але для API це означало б дірку в
  обліку; варто рахувати токени самостійно як fallback.
- Поріг gate (`evals/baselines.yaml`) — заглушка до виміру розкиду між
  повторами baseline.

## 2026-11-07 · Фаза 4. Observability

**Питання дня.** Як з будь-якого провального прогону за один крок дістати
його повну історію (хід → виклик моделі → інструмент) і не злити при цьому
секрети?

**Розглянуті варіанти** (записано до реалізації).
- Бекенд трейсів: Phoenix локально · Langfuse Cloud · OTLP у файл. Phoenix і
  Langfuse — окремі сервіси (на 7 ГБ RAM поруч з Ollama і Docker тісно);
  Langfuse Cloud — дані назовні. → OpenTelemetry SDK з вибором експортера:
  JSONL-файл за замовчуванням, OTLP для Phoenix за бажанням, плюс
  `agent trace show <id>` замість UI.
- Що класти в span: повні повідомлення · тільки метрики й ідентифікатори.
  Повідомлення містять код користувача і вивід команд, тобто потенційні
  секрети. → за замовчуванням тільки метрики, назви інструментів, рішення
  permissions; вміст — ні. Траєкторії з вмістом уже лежать у results JSON.
- Redaction: SpanProcessor на виході · на вході при встановленні атрибута.
  `ReadableSpan` незмінний, тож процесор на виході не може переписати
  атрибути. → redaction у єдиній точці встановлення атрибутів.
- Атрибути: власні імена · GenAI semantic conventions (`gen_ai.*`). → GenAI
  semconv, де вони є, `agent.*` для решти (ціна, TTFT, ревізія, verdict).

**Що зроблено.**
- `agent.telemetry`: OpenTelemetry, експортери `file` (JSONL, за
  замовчуванням `~/.local/state/agent/traces.jsonl`), `console`, `otlp`.
- Дерево span-ів: `invoke_agent` → `agent.turn` → `chat {model}` /
  `execute_tool {name}`; атрибути GenAI semconv + `agent.*` (ревізія, ціна,
  TTFT, спроби, verdict, exit code, команда bash).
- Redaction ключів (OpenAI/OpenRouter/Anthropic, GitHub, HF, AWS, Bearer,
  `*_KEY=`/`*_SECRET=`/`*_TOKEN=`, приватні ключі, email) у єдиній точці
  встановлення атрибутів. Вміст повідомлень у span-и не йде — є тест.
- `trace_id` у headless JSON, у REPL, у кожному eval-записі й у таблиці
  провальних прогонів звіту; `agent trace list | show <id> | stats`
  (p50/p95 latency і TTFT, вартість на прогін, частка збоїв інструментів).

**Числа.** 258 тестів зелені (19 нових для телеметрії). Живого прогону з
трейсами на моделі ще не було.

**Що досі незрозуміло / не зроблено.**
- Phoenix через `--trace otlp` не перевірений.
- Online-метрики (👍/👎, частка прийнятих diff, `/undo`) — не зроблені;

- Критерій «готово» фази 4 (≥5 класів у таксономії з кейсами під кожен):

## 2026-11-08 · Фаза 5. Контекст, кешування, routing

**Питання дня.** Як дати агентові довгі сесії на моделі з 8K контексту і не
зламати кеш префіксу, за який платимо найменше?

**Розглянуті варіанти** (записано до реалізації).
- Рахувати токени: токенізатором моделі (потрібен `transformers` і
  завантаження токенізатора) · реальний `usage.input_tokens` останнього
  виклику + оцінка символи/3 для дописаного після нього. Сервер і так
  повертає точне число за кожен виклик. → друге; токенізатор — тільки якщо
  оцінка помилятиметься більше ніж на 20%.
- Коли стискати: при 90% (вже стоп) · при 70%. → 70%: лишає місце на
  відповідь і на сам виклик компакції.
- Що лишати після компакції: системний промпт, поточну задачу, підсумок,
  останні N повідомлень, розрізаючи тільки на межі, де tool-результати не
  відірвані від свого виклику.
- Routing: окрема модель для компакції (`--compact-model`), за
  замовчуванням та сама. Таблиця якість/вартість — коли буде 27B.
- Explorer subagent і todo: завжди · тільки коли контекст ≥ 32K. Кожна
  схема інструмента — ~150 токенів префікса; на 8K це відчутно. → за
  розміром вікна.
- Сесії: SQLite · JSONL. → JSONL, одне повідомлення на рядок, append-only.

**Що зроблено.**
- `core/context.py`: оцінка контексту (точний `usage` + символи/3 для
  дописаного), компакція при 70% вікна, розріз тільки там, де tool-результат
  не відривається від свого виклику; span `agent.compact`.
- AGENTS.md (або CLAUDE.md) з кореня репо додається до системного промпту;
  префікс сталий протягом сесії.
- `cache_hit_rate` у статистиці прогону, звіті CLI і JSON.
- Сесії в JSONL, `agent --resume <id|last>`, `agent sessions`.
- `todo_write` і `explore` (read-only subagent зі своїм контекстом і
  бюджетом) — вмикаються від вікна ≥ 32K.
- `--compact-model` — routing компакції й explorer на дешевшу модель.
- `core/builder.py`: одна збірка агента для CLI і evals.

**Числа.** 271 тест. Таблиця «конфіг → pass@1 / вартість / TTFT» (критерій
«готово» фази) потребує 27B: на 3B немає різниці між нулями. Скрипт для неї —
у GPU-наборі (`gpu/`).

**Що досі незрозуміло.** Наскільки оцінка «символи/3» розходиться з
токенізатором Qwen3.8 — перевірити на першому прогоні 27B (у `usage` є
точне число для порівняння).

## 2026-11-08 · Фаза 6. RAG по коду

**Питання дня.** Чи потрібен coding-агенту векторний пошук, якщо в нього вже
є `grep` і `glob`?

**Розглянуті варіанти** (записано до реалізації).
- Chunking: tree-sitter (план) · stdlib `ast` + вікна рядків. tree-sitter
  дає багато мов ціною нативних wheel-ів; усі задачі зараз на Python. →
  `ast` для `.py` (функції, класи, методи з рядками), вікна по 60 рядків з
  перекриттям 10 для решти. tree-sitter — коли з'явиться друга мова.
- BM25: `bm25s` · SQLite FTS5 · свій. FTS5 токенізує як текст і не ріже
  `parse_config` / `parseConfig` на слова. → свій, ~50 рядків, з
  код-токенізацією.
- Ембеддинги: `sentence-transformers` (torch, ~2 ГБ) · OpenAI-сумісний
  `/v1/embeddings` (Ollama, vLLM, будь-який провайдер). → другий, той самий
  model-agnostic принцип, що й для чату.
- Сховище: LanceDB · sqlite-vec · SQLite + numpy. На тисячах чанків точний
  пошук по numpy-матриці — мілісекунди. → SQLite для метаданих, `.npy` для
  векторів.
- Reranker: cross-encoder (torch) · без нього. → інтерфейс + опційний
  cross-encoder, якщо встановлено `sentence-transformers` (GPU-машина).
- Golden set для retrieval: з git-історії (повідомлення коміту → змінені
  `.py`-файли) реального репо.

## 2026-11-08 · Фаза 7. MCP

**Питання дня.** Як підключати чужі інструменти через MCP і не дати
серверу змінити їхній опис після того, як ми його схвалили?

**Розглянуті варіанти** (записано до реалізації).
- SDK: `mcp` 1.x (FastMCP) · 2.x (`MCPServer`). Пакет уже 2.3, FastMCP
  перейменований. → 2.x, без пінінгу на стару гілку.
- Довіра до опису інструмента: щоразу питати · пінити хеш при першому
  підключенні (TOFU) і блокувати інструмент, якщо хеш змінився. → TOFU,
  `agent mcp trust <server>` для свідомого оновлення.
- Права: всі MCP-інструменти як exec (питати в ask-режимі) · за конфігом
  сервера. → за конфігом, за замовчуванням exec; allowlist інструментів на
  сервер.
- Вивід: як є · обгорнутий у `<untrusted-tool-output>` з попередженням. →
  обгорнутий: це канал для непрямої prompt injection.

**Що зроблено.**
- `agent.mcp.server`: MCP-сервер `code-search` (tools `search_code`,
  `get_symbol`, resource `index://stats`) поверх індексу фази 6.
- `agent.mcp.client.MCPHub`: stdio-сервери з `configs/mcp.json` стають
  інструментами `mcp__<server>__<tool>` з permission-kind і allowlist.
- TOFU-пінінг хешів описів (`~/.local/state/agent/mcp_pins.json`); змінений
  опис вимикає інструмент; `agent mcp list`, `agent mcp trust <server>`.
- Вивід MCP загорнутий у `<untrusted-tool-output>`.

**Числа.** 290 тестів; MCP-тести ганяють справжній сервер по stdio
(namespacing, виклик, rug pull, allowlist, недоступний сервер).

**Що досі незрозуміло.** Сторонні сервери (git, GitHub з мінімальним
токеном) не підключені: потрібен токен автора. Streamable HTTP не
тестувався. Бонус «агент як MCP-сервер» не зроблений.
