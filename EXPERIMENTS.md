## 2026-11-07 · Фаза 0. Підготовка

**Питання дня.** Чи можна розробляти агента на 27B без локальної GPU і майже
без витрат, і що в плані треба змінити, перш ніж писати перший рядок клієнта?

**Розглянуті варіанти.**
- Розробка: 27B через hosted API з першого дня · мала модель локально в Ollama.
- Генерація траєкторій (фаза 9): API · орендована GPU з vLLM.
- Перевірка типів: pyright (як у плані) · mypy --strict (уже знайомий).
- Ліцензія: MIT · Apache-2.0.
- ADR: без них, усе в журналі · ADR на кожне рішення · 3–4 ADR на весь проєкт.
- Хто пише код: все пише автор · все пише Claude · розподіл за темою.

**Що зроблено.**
- Перевірено модель за сторонніми джерелами (HF був недоступний): Apache 2.0,
  262K контексту нативно, thinking увімкнений за замовчуванням.
- Перевірено tool calling на `qwen2.5:3b-instruct-q4_K_M` через Ollama.
- Скелет репо: uv, ruff, mypy --strict, pytest, Makefile, smoke-тест,
  CI на GitHub Actions, design doc, ADR 0001.

**Числа.**
- Tool calling на 3B локально: працює, `finish_reason: "tool_calls"`,
  правильний інструмент і аргументи (один ручний запит, не eval).
- `make check`: 10 тестів, усі зелені.
- Оцінка вартості фази 9 (розрахунок, не вимір): API ≈ $103 за 30M вихідних
  токенів проти ≈ $5–10 на орендованій GPU; вимкнення thinking зменшує
  API-оцінку з ≈ $130 до ≈ $50 на тисячу траєкторій.

**Висновок.**
- Фази 0–8 — на малій локальній моделі за $0; 27B тільки у фазах 3, 9, 10.
- Фаза 9 — на орендованій GPU, не в API.
- mypy --strict, Apache-2.0, 3–4 ADR на проєкт.
- Обв'язку пише Claude; цикл агента, інструменти, sandbox, permissions,
  метрики evals і оракули пише автор.

**Що досі незрозуміло.**
- Офіційні факти про модель: commit-ревізія на HF, чи є окремий
  Instruct-варіант, формат tool calls у chat template.
- Чи допомагає thinking coding-агенту настільки, щоб виправдати вартість —
  вимірюється у фазі 3.
- `usage` в Ollama не має лічильника reasoning-токенів; як його повертає
  провайдер 27B — перевірити у фазі 1.

## 2026-11-07 · Фаза 1. Шар доступу до моделі

**Питання дня.** Як зробити один клієнт, що однаково працює з Ollama і з
hosted 27B, ретраїть тільки те, що можна, і рахує токени, гроші, latency і
TTFT на кожен виклик?

**Розглянуті варіанти** (записано до реалізації).
- Sync чи async клієнт: sync простіший · async дає паралельний eval runner у
  фазі 3 без потоків. → async.
- Retry: `tenacity` (уже в залежностях) · вбудовані retry `openai` SDK ·
  власний цикл. Вбудовані не відрізняють retry до першого токена і посеред
  стріму, `tenacity` ховає логіку за декораторами. → власний цикл з
  ін'єкцією `sleep` і `rng` для тестів, SDK retry вимкнені (`max_retries=0`),
  `tenacity` прибрати.
- Retry посеред стріму: ретраїти завжди · тільки до першого токена. Після
  першого токена користувач уже бачив частину відповіді. → тільки до першого
  токена.
- Backoff: експоненційний без jitter · equal jitter · full jitter. → full
  jitter, `Retry-After` має пріоритет, якщо сервер його дав.
- Мокання HTTP у тестах: `pytest-httpserver` (справжній сервер) · `respx`
  (мок транспорту httpx, на якому стоїть `openai`). → `respx`, швидше й
  детерміновано.
- Ревізія локальної моделі: тег Ollama · digest. Тег рухомий. → digest у
  конфізі.
- Під час реалізації: `openai` SDK 3.x працює на `httpx2`, а `respx` патчить
  тільки `httpx`. → замість `respx` тести підставляють
  `httpx2.MockTransport` через `http_client`. Ще один фейковий сервер не
  потрібен.

**Що зроблено.**
- `configs/models.yaml`: `local-small` (qwen2.5 3B), `local-tiny` (0.5B),
  `qwen27b-hosted` (OpenRouter). Локальні моделі запінені на digest, hosted —
  на датований знімок.
- `llm/`: стрімінговий async-клієнт, класифікація помилок, full-jitter
  backoff з пріоритетом `Retry-After`, загальний дедлайн, облік токенів
  (включно з cached і reasoning), вартості, latency, TTFT і швидкості
  декодування. `reasoning_content` / `reasoning` іде окремо від `content`.
- CLI: `agent chat` (one-shot і REPL), `agent models`.
- Тести: 64 юніт-тести без мережі; 2 живі (`make test-live`) на Ollama.

**Числа** (ноутбук, CPU, Ollama 0.34.2, 5 викликів, промпт 40 токенів,
`max_tokens=80`, після прогріву).

| модель | TTFT, медіана | latency, медіана | декодування, медіана |
|---|---|---|---|
| `local-tiny` (0.5B Q8) | 0.03 с | 1.82 с | 44.6 tok/s |
| `local-small` (3B Q4_K_M) | 0.10 с | 6.60 с | 11.9 tok/s |

- TTFT такий малий, бо Ollama кешує префікс: 39 із 40 вхідних токенів
  прийшли як `cached_tokens`. Холодний перший виклик 3B — 0.48 с.
- Живий tool call на 3B: правильний інструмент і аргументи (2/2 живих
  тести).

**Висновок.**
- Клієнт однаковий для будь-якого OpenAI-сумісного endpoint; модель
  перемикається аліасом.
- 12 tok/s на 3B означає, що агентна задача на 2–3 тисячі вихідних токенів
  займе кілька хвилин. Для розробки циклу прийнятно, для evals на ноутбуці —
  ні: eval-прогони фази 3 мусять іти на 27B через API.
- **Контекст Ollama — 4096 токенів**, хоча модель підтримує 32K, і через
  OpenAI-сумісний endpoint це не змінити. Схеми інструментів плюс історія
  швидко це переповнять, а Ollama обріже промпт мовчки. Перед фазою 2
  треба або запустити Ollama з `OLLAMA_CONTEXT_LENGTH=16384` (KV cache 3B ≈
  36 КБ/токен → ≈ 0.6 ГБ на 16K), або рахувати бюджет під 4K.

**Що досі незрозуміло.**
- Критерій «`--model qwen27b-hosted` поводиться так само» **не перевірений**:
  потрібен ключ OpenRouter, тобто гроші автора. Код шляху той самий, тест
  на відсутній ключ є.
- Як OpenRouter стрімить `reasoning` для Qwen3.8 і чи віддає
  `reasoning_tokens` у `usage` — перевірити з першим ключем.
- `Retry-After` у форматі HTTP-дати ігнорується (падаємо на backoff) —
  свідомо, поки не зустрінеться провайдер, який так робить.
